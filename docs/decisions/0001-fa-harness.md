# ADR 0001 — FA harness по семи слоям ETCLOVG

- Статус: superseded by [ADR 0002](0002-one-task-and-model-fallback.md)
- Дата: 2026-11-18
- Владелец: @lqsaf

> Решение о непрерывном цикле внутри одного job заменено в ADR 0002:
> один запуск выполняет ровно одну задачу, модели переключаются внутри шага.

## Контекст

Проекту нужен агент, который развивает репозиторий без человека и без его ноутбука. Старый «ночник» запускался раз в час, выполнял одну задачу и уходил; лимиты и проверки жили в промпте, а успех определялся по тексту ответа. Это давало три проблемы:

1. Работа останавливалась между запусками, а не шла непрерывно.
2. Агент мог «запомнить» прогресс, которого нет в репозитории (state hole).
3. Не было детерминированных инвариантов, бюджетов и kill switch.

Одновременно появилась таксономия Harness Engineering: Execution, Tools, Context, Lifecycle, Observability, Verification, Governance (ETCLOVG) и четыре функции OpenAI — Constrain, Inform, Verify, Correct.

## Решение

Построить FA (free agent) как harness вокруг OpenCode:

- **Execution**: GitHub Actions, один job до ~5 ч 50 мин, изначальный watchdog каждые 15 минут (расписание изменено на 30 минут решением ADR 0002), `concurrency: fa-loop`, лимиты в коде.
- **Tools**: детерминированные скрипты на Node stdlib, единый контракт exit 0/1/2, allowlist shell-команд.
- **Context**: `AGENTS.md` + `docs/CONVENTIONS.md` + контекст задачи + skill `fain`, компакция и лимиты вывода.
- **Lifecycle**: очередь `TASKS.md`, ветка `fa/work`, rolling PR в `main`, откат при провале, `[!]` после лимита попыток.
- **Observability**: JSONL-события, метрики, `summary.json`, artifacts, issues, `STATUS.md`.
- **Verification**: инварианты (`npm run verify`) → замеры (`fa:eval`) → человек/reviewer.
- **Governance**: ordered deny-правила, защищённые пути, branch protection, CODEOWNERS, hook, kill switch.

Агент не коммитит и не пушит. Оркестратор проверяет фактический diff, запускает проверки и только потом коммитит. Пустой diff при ответе «готово» — провал.

## Последствия

Положительные:

- Проект работает без ноутбука и без ручного запуска.
- Успех доказан состоянием (diff + verify), а не словами модели.
- Стоимость ограничена бюджетом времени и токенов.
- Инциденты превращаются в инварианты или замеры.
- Merge остаётся за человеком.

Отрицательные и компромиссы:

- Нужны секреты провайдера и branch protection.
- `GITHUB_TOKEN` не триггерит workflow из PR; для этого нужен `FA_PAT`.
- Merge-конфликты останавливают цикл и требуют человека.
- Модель недетерминирована; инварианты снижают риск, но не отменяют ревью.
- Один rolling PR может стать большим; человек может мержить его чаще.

## Альтернативы

1. **Оставить nightly.** Дешевле, но не решает непрерывность и state hole.
2. **Cron каждую минуту.** Больше запусков, но каждый запуск холодный; нет непрерывного контекста и накопления работы.
3. **Локальный демон.** Требует ноутбук и сеть; противоречит цели.
4. **Полный MCP-стек.** Добавляет сетевую поверхность и недетерминизм без пользы для текущего масштаба.
