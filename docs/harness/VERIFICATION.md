# Verification — три уровня проверок

Слой отвечает на вопрос **«стало лучше или хуже?»** без настроения, маркетинга провайдера и «посмотрел глазами».

## Уровень 1 — инварианты в коде

Мгновенно, бесплатно, без модели. Зашиты в `scripts/verify.mjs`.

| Инвариант | Что ловит |
| --- | --- |
| `js.syntax` | синтаксис всех `js/*.js` и `worker.js` |
| `i18n.parity` | пропущенные/лишние/пустые ключи ru/en/zh |
| `storage.keys` | неверный формат `fain_*_vN`, дубли, хардкод |
| `html.contract` | `getElementById` без элемента, дубли id, битые ссылки |
| `css.integrity` | небалансированные скобки, отсутствующие `url()` |
| `feed.schema` | структура `feed.json`, дубли ID, даты |
| `opencode.config` | битый JSONC, deprecated-поля, несуществующий агент |
| `models.registry` | пустой/битый список моделей, дубли ID, неверная классификация quota |
| `queue.protocol` | дубли ID, битые статусы, >1 claimed, неизвестные зависимости |
| `package.json` | отсутствие `scripts.verify`, `type: module` |
| `diff.guard` | секреты в добавленных строках, размер диффа |
| `diff.protected` | правка harness-файлов агентом |

Правило: инвариант должен быть **замкнут на ответе**, одинаковым сегодня и через год, без исключений. Если проверка зовёт модель или имеет законные исключения — это не инвариант, а эвристика; ей не место в коде.

## Уровень 2 — замеры

`scripts/fa/eval.mjs` и метрики. Дорого, запускается по событию:

- смена модели/провайдера;
- крупное изменение промпта;
- подозрение на деградацию (рост шагов, повторных вызовов, ошибок).

Замер: фиксированная микрозадача в чистой копии репозитория, одинаковый промпт, одинаковые проверки. Считаем pass/fail, шаги, токены, время, размер диффа. Сравниваем с эталоном в [PROMPTS.md](PROMPTS.md).

```bash
npm run fa:eval -- --suite model --models xerosharc/claude-haiku-5-5,google/gemini-3.1-flash-lite
```

## Уровень 3 — человек

- Merge PR: вкус, продукт, UX, тексты, архитектурные компромиссы.
- Разблокировка `[!]`: задача требует решения, которого нет в коде.
- Смена модели и приёмка замеров.
- Инциденты безопасности.

Reviewer-сабагент (`fa-reviewer`) — **вероятностная** проверка. Он может ошибаться, поэтому его вердикт не заменяет инварианты и человека. В deterministic-слое модели нет.

## Model-as-judge

Используется только как дополнительный сигнал:

- проверяет diff против acceptance;
- ищет пропущенные края и регрессии;
- отвечает `VERDICT: PASS` или `VERDICT: FAIL` + замечания.

Он не может отменить `verify` и не может разрешить запрещённые действия. При `review: required` его FAIL блокирует коммит, но PASS не отменяет инварианты.

## Защита от подыгрывания

- Агент не может править `TASKS.md`, `verify.mjs`, workflow и правила.
- Проверки запускает оркестратор, а не агент.
- Успех = фактический дифф + зелёный `verify`, а не текст ответа.
- `BLOCKED` — нормальный исход; «зелёный любой ценой» запрещён.
- Секреты и запрещённые пути проверяются после агента, а не до.

## Definition of Done

1. Изменения строго по acceptance.
2. `verify` зелёный (и задача-специфичная команда, если есть).
3. Нет правок защищённых файлов, секретов, новых зависимостей.
4. Дифф минимален; нет drive-by рефакторинга.
5. Для `review: required` — `VERDICT: PASS`.
6. Человек может откатить одним revert коммита.

## Как добавить проверку

1. Опиши инвариант словами: что всегда верно.
2. Проверь три вопроса: замкнут ли на ответе, одинаков ли через год, есть ли исключения.
3. Если да — добавь в `verify.mjs` с понятным сообщением.
4. Если нет — добавь замер в `eval` или оставь человеку.
5. Прогони на текущем репозитории: проверка не должна падать на здоровом коде.
