# Observability — логи, метрики, алерты

Слой отвечает за то, чтобы поломки были видны **в момент поломки**, а не по жалобе пользователя.

## Что пишется

| Артефакт | Путь | Содержимое |
| --- | --- | --- |
| События оркестратора | `fa/logs/<run>/run.jsonl` | claim, run, verify, commit, retry, stop |
| События OpenCode | `fa/logs/<run>/<task>.jsonl` | шаги, tool calls, ошибки, токены |
| stderr OpenCode | `fa/logs/<run>/<task>.err.log` | диагностика процесса |
| Результат проверок | `fa/logs/<run>/verify-<task>.json` | errors/warnings/checks |
| Сводка | `fa/logs/<run>/summary.json` | длительности, попытки, диффы |
| Статус | `fa/logs/STATUS.md` | таблица очереди и последний запуск |
| GitHub artifact | `fa-logs-<run>` | всё вышеперечисленное, `if: always()` |
| PR body | автоматически | статус очереди и последние задачи |
| Issue | `FA blocked: Txx` | причина блокировки и ссылка на лог |

## Метрики (`scripts/fa/metrics.mjs`)

- количество шагов и tool calls;
- распределение по инструментам (`read`, `edit`, `shell`, ...);
- повторяющиеся вызовы одного инструмента с теми же аргументами;
- ошибки инструментов и их доля;
- токены (input/output/reasoning/cache) и стоимость, если провайдер их отдаёт;
- длительность задачи и всего запуска;
- файлы и строки диффа.

Парсер терпим к схеме событий: ищет поля рекурсивно, не падает на неизвестных событиях. Если схема изменится, метрики деградируют, но цикл не сломается.

## Детект плохих циклов

- Один и тот же `(tool, args)` ≥ 3 раз подряд → флаг `repeated_calls`.
- Больше 40 шагов без изменения файлов → флаг `no_progress`.
- Доля ошибок инструментов > 50% → флаг `tool_errors`.
- Токены выше `FA_TOKEN_BUDGET` → остановка запуска.

Флаги не убивают задачу автоматически (кроме бюджета), но попадают в `summary.json` и в PR body. Это сигнал человеку и материал для правки промпта/лимита.

## Алерты

- Блокировка задачи → issue с причиной, ID, ссылкой на PR и последними 20 строками ошибки (без секретов).
- 3 инфра-провала → issue `FA infrastructure failure` и остановка.
- Упавший `verify` в PR → GitHub check (`fa-verify.yml`) и красный статус.
- Ошибки в job → аннотация `::error::` с ID задачи.

## Расследование

1. Открой artifact `fa-logs-<run>`.
2. Найди `summary.json`: какая задача, сколько шагов, где упало.
3. Открой `<task>.jsonl`: последние tool calls и ошибки.
4. Сверь с `verify-<task>.json`: инвариант или среда.
5. Если повторяется — добавь инвариант в `verify` или замер в `eval`, а не правь промпт наугад.

## Приватность

- Ключи, токены и `.env` не логируются; `policy.mjs` редактирует совпадения.
- Тела RSS-статей в логи не пишутся целиком: только заголовки/ID.
- Логи живут 14 дней (artifact retention), затем удаляются.
- Публичный репозиторий = публичные логи; не добавлять в них чувствительные данные.

## Что считается нормой

- Успешная задача: 5–25 шагов, 1–2 tool calls на файл, 0 повторных вызовов.
- Один запуск: 3–10 задач до бюджета.
- Если среднее число шагов растёт после смены модели — это сигнал к замеру, а не к «модель тупеет».
