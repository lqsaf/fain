# Security policy

## Поддерживаемые версии

Проект живёт в `main`; исправления безопасности выходят только туда. Отдельных LTS-веток нет.

## Как сообщить

Не открывай публичный issue с деталями уязвимости. Используй GitHub Private Vulnerability Reporting в разделе **Security → Advisories → Report a vulnerability**. Если он недоступен — напиши владельцу репозитория без публикации деталей.

В отчёте укажи: затронутый файл/endpoint, шаги воспроизведения, влияние и, если есть, минимальный PoC. Не прикладывай реальные ключи и персональные данные.

## Что входит в периметр

- `worker.js` и `wrangler.toml`: утечка ключей, обход токена `POST /refresh`, инъекции в RSS/HTML, SSRF, отказ в обслуживании.
- Frontend (`js/`, HTML, CSS): XSS через данные ленты, небезопасный `innerHTML`, утечка localStorage.
- Harness (`.github/`, `scripts/fa/`, `.opencode/`, `opencode.jsonc`): обход запретов агентом, подмена проверок, кража `GITHUB_TOKEN`/`FA_PAT`, prompt injection.
- Цепочка поставок: новая зависимость, изменённый workflow, подозрительный action.

## Правила для секретов

- Ключи хранятся только в GitHub Secrets и переменных окружения.
- `.env`, `.dev.vars`, `~/.ssh`, `~/.aws`, `~/.config/gh` не читаются агентом и не коммитятся.
- Ключи не пишутся в логи, PR body, issues и artifacts.
- При подозрении на утечку: остановить FA (`FA_ENABLED=false` или `FA_STOP`), отозвать ключ, удалить artifact, проверить diff, выпустить advisory.

## Границы

- Merge в `main` делает человек; auto-merge выключен.
- Агент не деплоит, не публикует и не меняет данные.
- `scripts/verify.mjs` и `scripts/fa/policy.mjs` — защищённые файлы; их меняет только владелец.
- Сообщения об ошибках без влияния на безопасность — обычный issue.

## Что не считается уязвимостью

- Нужен доступ к секрету, которого у атакующего нет.
- Self-XSS, требующий вставить код в консоль.
- Отсутствие заголовков, не влияющее на проект.
- Теоретические атаки без воспроизведения.
